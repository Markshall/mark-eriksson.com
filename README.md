# mark-eriksson.com

Source for **[mark-eriksson.com](https://www.mark-eriksson.com)**, the portfolio and CV of Mark Eriksson, a full-stack developer.

It's a single static page with a light/dark theme, a filterable project gallery with desktop and mobile screenshots of each site, and an experience timeline. There's no framework: just HTML, CSS and TypeScript, built with [Vite](https://vite.dev).

## Quick start

```shell
docker compose up
```

That starts the Vite dev server with hot reload at http://localhost:5173. Dependencies are installed inside the container and reinstalled automatically when `package-lock.json` changes.

If you'd rather run it without Docker, use Node 24+:

```shell
npm install
npm run dev
```

## Project layout

```
src/
  index.html         The page
  styles/            CSS
  scripts/           TypeScript: theme toggle, project gallery, page behaviour
  data/projects.ts   The list of projects, shared by the site and the screenshot script
  assets/            Images processed and hashed by Vite, including project screenshots
  projects/          Project pages, generated by scripts/pages.ts (git-ignored)
templates/           The layout the generated pages are built from
public/              Copied as-is to the site root (favicons, og-image, ads.txt, .htaccess)
scripts/             Page generator, screenshot capture and deploy scripts
dist/                Build output, which is what goes on the server (git-ignored)
```

## Scripts

| Command                | What it does                                |
| ---------------------- | ------------------------------------------- |
| `npm run dev`          | Start the dev server                        |
| `npm run typecheck`    | Check TypeScript types                      |
| `npm test`             | Build, then run the smoke tests             |
| `npm run format`       | Format all files with Prettier              |
| `npm run format:check` | Check formatting without changing files     |
| `npm run build`        | Type-check, then build to `dist/`           |
| `npm run preview`      | Serve `dist/` locally                       |
| `npm run lighthouse`   | Build, then audit the pages with Lighthouse |
| `npm run screenshots`  | Capture project screenshots (see below)     |
| `npm run deploy`       | Build and upload to the server (see below)  |

Absolute URLs in `src/index.html` (`og:url`, `og:image`) use `%VITE_SITE_URL%`, which is set in `.env.development` (localhost) and `.env.production` (the live domain).

## Tests

`tests/` has Playwright smoke tests for the built site, run against `vite preview` (config in `playwright.config.ts`). `npm test` builds first; if `dist/` is already built, `npx playwright test` runs them alone. They cover:

- **Consent:** nothing loads from Google Tag Manager until the visitor accepts, and Reject and Accept are both remembered.
- **Project gallery:** project links, filters, the arrow keys and pager, both screenshots for every project, and the screen-reader announcement when the project changes.
- **Project pages:** every `/projects/<id>/` page loads without errors, with its title, canonical URL, preview image, screenshots and previous/next links. Scores appear only where a project has them, and the Details button, back link and sitemap all point to the right places.
- **Theme:** the page follows the system setting until the visitor picks a theme, then keeps their choice.
- **Pages:** `/`, `/privacy/` and `/404.html` load without console errors, and the hero stats and footer year are right with JavaScript turned off.

They use your installed Google Chrome, like the screenshot script, so there's no browser download. The tests never reach the internet: GTM requests get an empty script, and any other request off the site is blocked and fails the test. A new third-party request therefore has to be added deliberately in `tests/fixtures.ts`.

## Adding a project

Projects are listed in `src/data/projects.ts`. Each one gets a full-page desktop (1440px) and mobile (390px) screenshot, saved as `src/assets/screenshots/<id>-desktop.webp` and `<id>-mobile.webp`. Only these full-size captures are committed: at build time, [vite-imagetools](https://github.com/JonasKruckenberg/imagetools) resizes them into smaller copies (`SRCSETS` in `src/scripts/screenshots.ts`) and the browser picks the one that fits the screen.

Add the project to `src/data/projects.ts`, then capture its screenshots:

```shell
npm run screenshots                  # capture projects with no screenshots yet
npm run screenshots -- crown-oil     # recapture specific project ids
npm run screenshots -- --all         # recapture everything
```

This runs on your machine rather than in Docker and drives your installed Google Chrome. Cookie banners, chat widgets and other floating overlays are hidden before each capture.

A few things to know when a capture goes wrong:

- If a site is down or times out (60s to load), that view is skipped, the rest carry on, and the script exits non-zero listing what failed. Any existing screenshot for the failed view is left untouched, so re-run with just those ids.
- Pages taller than 16,383px (WebP's limit) are cropped at that height, with a warning.
- Videos are frozen on their last frame and the page is scrolled through first so lazy-loaded images appear. If a site still looks wrong, check it in Chrome with reduced motion turned on, because that's how it's captured.

### Retired projects

When a site is replaced or taken down, keep it listed and set its `retired` field: the year it went offline, a [Wayback Machine](https://web.archive.org) snapshot timestamp, and (if it was rebuilt) the id of the project that replaced it. Retired projects are listed after the live ones and labelled "retired". Their links go to the archived copy, or nowhere if there's no snapshot. The screenshot script captures them from the snapshot (without the archive's toolbar), allowing 180s for it to load. Their pages show the years they were live and link to the project that replaced them, and that project's page links back. Leave out `scores`, since there's no live site to measure.

## Project pages

Each project in `src/data/projects.ts` also gets its own page at `/projects/<id>/`. It shows the summary, role, year, stack, the GTmetrix scores if there are any, both screenshots, the `body` write-up (one string per paragraph), and links to the previous and next projects. The gallery's "Details" button links to it.

`scripts/pages.ts` builds each page from `templates/layout.html` (the shared `<head>`, header and footer) plus its own `<main>`. It writes them into `src/projects/` (git-ignored), so Vite builds them like any other page. The pages are regenerated before every build and dev server start, and again in dev when a source file changes. They're added to the sitemap. Edit the header and footer in `templates/layout.html` as well as in `src/index.html`.

- **Scores** come from each project's `scores` (GTmetrix performance and structure, LCP, TBT and CLS). They're labelled with `SCORES_MEASURED`, so update that when you re-measure. Leave `scores` out to hide them.
- **Link previews:** each page's preview image (`/img/projects/<id>.jpg`) is a 1200×630 crop of the top of the desktop screenshot, made at build time.
- **Screenshots:** their `srcset` is filled in by `src/scripts/project-page.ts` from the same resized files the gallery uses, because Vite doesn't resize images linked from HTML.

## Editing the page

Apart from the project gallery and the generated pages above, everything is plain HTML in `src/index.html`:

| Section                     | Where                                                   |
| --------------------------- | ------------------------------------------------------- |
| Hero intro and buttons      | `<section class="hero">`                                |
| Experience, skills chips    | `<section id="resume">`, one `.job-head` block per role |
| Contact email, social links | `<footer id="contact">`                                 |
| Page title, description, OG | `<head>`                                                |

The hero stats and footer year are worked out in `src/data/stats.ts`: years since `CAREER_START`, the number of projects, and the number with category `Personal`. The `page-stats` plugin in `vite.config.ts` writes them into the built HTML, into the element with the matching data attribute (`data-years`, `data-project-total`, `data-personal-total`, `data-year`), so the numbers typed in the HTML are overwritten and can be left as they are. The years and footer year are also refreshed in the browser, in case the site isn't rebuilt for a while.

Each project has a shareable link, `/#projects/<id>`, using the `id` from `src/data/projects.ts`. Opening one selects that project and scrolls to the gallery. As visitors browse, the address bar updates to match without adding history entries. In the gallery, the left and right arrow keys step through projects, and up and down do the same while focus is in the list.

`src/privacy/index.html` is the privacy and cookies page, served at `/privacy/` and linked from the footer and the cookie banner. It lists the Google Analytics cookies, so update it if the GTM container starts running other tags. The 404 and privacy pages share `src/scripts/page.ts` and the site's stylesheet.

`src/404.html` is the not-found page, built as a second Vite entry. `public/.htaccess` tells Apache to serve it for missing URLs (`ErrorDocument 404 /404.html`), which needs `AllowOverride` to include `FileInfo` for the web root.

## Theming

Colours are CSS custom properties in `src/styles/tokens.css`. Each theme colour is written once as `light-dark(<light>, <dark>)`, so change both values in the same place. The projects band is dark in both themes and has its own `--band-*` tokens.

By default the page follows the system light/dark setting. The toggle (`src/scripts/theme.ts`) sets `data-theme` on `<html>`, which overrides `color-scheme`, and remembers the choice in `localStorage`. Until a visitor clicks the toggle, the page keeps following system changes.

## Headers and caching

`public/.htaccess` sets the response headers. It needs `mod_headers`, and `AllowOverride` must include `FileInfo` (as `ErrorDocument` already does). If `mod_headers` is missing, the headers are quietly skipped, so check them after deploying with `curl -I https://www.mark-eriksson.com/`.

- **Security headers** on every response: HSTS, `X-Content-Type-Options` and `Referrer-Policy`. Everything except `/check/` also gets a Content-Security-Policy, `X-Frame-Options`, `Cross-Origin-Opener-Policy` and `Permissions-Policy`. `/check/` is left out because it's deployed separately and loads Google Fonts, AdSense and inline scripts.
- **The CSP** allows scripts from this site and Google Tag Manager only. Inline scripts (the theme script in each `<head>`) are allowed by hash. The `csp-hashes` plugin in `vite.config.ts` hashes them after each build and writes the hashes into `dist/.htaccess` in place of `__INLINE_SCRIPT_HASHES__`, so editing one can't leave a stale hash. If the GTM container starts running other tags (or Custom HTML tags), add their hosts to the CSP or they'll be blocked; the browser console names what was blocked.
- **Caching:** files in `/assets/` have content-hashed names, so browsers cache them for a year (`immutable`). HTML pages are revalidated on every visit (`max-age=0`), which costs a 304 when nothing changed and means a returning visitor never gets an old page pointing at assets the deploy deleted. `s-maxage` still lets Cloudflare cache them, and the deploy purges the changed ones. Other files that keep their URLs (favicons, link preview images, `sitemap.xml`, `robots.txt`, `ads.txt`) are cached for a day.

The skill logos on the résumé are served as separate SVG files rather than inlined into the stylesheet (`assetsInlineLimit` in `vite.config.ts`), which keeps the CSS every page waits for small.

## SEO and static files

`sitemap.xml` and `robots.txt` are generated at build time by the `seo-files` plugin in `vite.config.ts`, using `VITE_SITE_URL`:

- `sitemap.xml` lists the pages in `PAGES` in `vite.config.ts`. Each `<lastmod>` is the date of the last commit that touched that page's files (or today, if git isn't available).
- `robots.txt` allows everything and points to the sitemap.

`src/index.html` also has a `<link rel="canonical">` and a JSON-LD `Person` block (name, job title, employer, skills, GitHub and CodePen profiles). Update the JSON-LD when the résumé changes.

The rest is updated by hand:

- `public/ads.txt` declares the Google AdSense publisher ID. Keep it if AdSense is in use on the domain.
- `public/img/og-image.png` (1200×630) is the link preview image. Replace it in place if the design changes.
- Google Tag Manager (`GTM-PV3S2MV`) only loads after the visitor accepts cookies, as UK GDPR and PECR require. `src/scripts/consent.ts` sets Google Consent Mode to denied, adds the cookie banner (its text is in that file) until the visitor chooses, and remembers the choice in `localStorage`. "Cookie settings" in the footer reopens the banner. Rejecting after accepting switches Consent Mode back to denied and deletes Google's `_ga`/`_gcl` cookies. There's no `<noscript>` fallback, because it would load GTM without asking.

## Deploying

Pull requests into `master` run `.github/workflows/check.yml`, which checks formatting, builds the site, runs the smoke tests and audits it with [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci), but never deploys. Only the merge deploys. The Lighthouse settings are in `lighthouserc.json`. It audits `/`, `/privacy/`, `/404.html` and one project page (`/projects/crown-oil/`) three times each and fails the check if accessibility drops below 100, SEO below 100 (except on the `noindex` 404 page) or best practices below 95. Performance only warns, because shared runners give noisy scores. The HTML reports are attached to the workflow run as `lighthouse-reports`. Run `npm run lighthouse` to audit locally; the reports go to `.lighthouseci/reports/`. `@lhci/cli` runs through `npx` at a pinned version rather than from `package.json`, because its dependencies have open `npm audit` advisories.

[Dependabot](https://docs.github.com/en/code-security/dependabot) (`.github/dependabot.yml`) opens dependency PRs every Monday: one grouped PR for npm minor and patch updates, a separate one for each npm major, and one for GitHub Actions. They go through the same Check workflow. Merging one that changes `package-lock.json` deploys the site.

Pushing to `master` runs `.github/workflows/deploy.yml` when the push touches something that affects the built site (`src/`, `public/`, `templates/`, the page generator, dependencies, build config, or the deploy script and workflow themselves). Commits that only change the README, docs or other tooling don't deploy. You can also run it by hand from the Actions tab. The workflow builds the site and uploads `dist/` with rsync over SSH. The server's SSH port is firewalled, so the runner joins the tailnet first and connects to the server's Tailscale address. It needs these repository secrets:

| Secret                 | Value                                             |
| ---------------------- | ------------------------------------------------- |
| `DEPLOY_HOST`          | Server's Tailscale IP (`tailscale ip -4`)         |
| `DEPLOY_USER`          | SSH user                                          |
| `DEPLOY_PATH`          | Web root, e.g. `/var/www/mark-eriksson.com`       |
| `DEPLOY_PORT`          | Optional, defaults to 22                          |
| `DEPLOY_SSH_KEY`       | Private key for a deploy-only key pair            |
| `DEPLOY_KNOWN_HOSTS`   | Output of `ssh-keyscan <DEPLOY_HOST>`             |
| `TS_OAUTH_CLIENT_ID`   | Tailscale OAuth client ID (auth keys write scope) |
| `TS_OAUTH_SECRET`      | Tailscale OAuth client secret                     |
| `CLOUDFLARE_ZONE_ID`   | Optional, Cloudflare zone ID for the site         |
| `CLOUDFLARE_API_TOKEN` | Optional, token with only Zone → Cache Purge      |

The OAuth client must be allowed to create devices tagged `tag:ci`. See [docs/deploying.md](docs/deploying.md) for how the whole flow works, setup from scratch, and troubleshooting.

To deploy by hand, copy `.env.example` to `.env`, fill it in, then:

```shell
./scripts/deploy.sh -n   # dry run
npm run deploy           # build + upload
```

The upload uses `rsync --delete`, so anything in the web root that isn't in `dist/` is removed, apart from `.well-known/` and `check/`, which are managed separately. Do a dry run first.

After the upload, any changed file that keeps its URL (`index.html`, `sitemap.xml`, favicons and so on) is purged from Cloudflare's cache. Hashed files in `assets/` get a new URL when they change, so they're skipped. The purge only runs when both Cloudflare settings are set, and a dry run lists what it would purge.
